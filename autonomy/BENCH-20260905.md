## Production defect: navigation support outside schematic bounds

Baseline `2bc29084` (`20260905-154155-suite`) built all 120 ring targets in 1,380
ticks (104.3 blocks/min), and the old target-only RCON audit confirmed 120/120.
The full-region audit failed. RCON independently confirmed cobblestone left at
`65,-60,67` and `66,-59,67`, both outside the ring's schematic box. Raw evidence:
`2bc29084-full-region-audit.log/json` and `2bc29084-leftover-scaffolds.log`.

The navigation placement policy allows supports outside schematic bounds, while
`isScaffoldLeftBehind` rejects all such positions to avoid breaking somebody
else's blocks. Full recalculation also visits only the schematic box. Consequently
the builder has neither ownership evidence nor cleanup work for those placements.

The production patch records requested AIR-to-throwaway placements at the common
interaction boundary, excludes requested schematic cells, and requires matching
server block-update evidence before granting cleanup authority. Both single and
section block updates use the existing event bus after application to the world.
Ownership ends only on an authoritative different state, including server AIR.
Local predicted AIR cannot erase an outstanding cleanup obligation. Missing
placement confirmation after 400 builder ticks triggers a named failure with the
affected coordinates; it never clears ownership to manufacture success.

Owned support is eligible for the existing nearby cleanup, with the existing
footing and active-route guards. The final cleanup phase feeds remaining owned
positions as AIR goals to the existing break and route machinery, uses the full
schematic to preserve target blocks, and starts routes with the no-placement lane.
The process cannot report completion while confirmed owned supports remain.

The first implementation run `77b3c4f7` (`20260905-155419-suite`) confirmed both
supports but correctly ended STALLED instead of SUCCESS. It exposed an interaction
between `BetterBlockPos` and vanilla `BlockPos`: equal coordinates use different
hash functions, so mixed position objects caused cleanup work to disappear from
goal assembly. All new ownership and cleanup keys now use packed coordinates.
The regression test deliberately records using `BetterBlockPos` and confirms using
vanilla `BlockPos`.

Independent root review also caught an unsafe local-state pruning path; it was
removed before acceptance. Tests now cover prediction-only placement, existing
blocks, target cells, rejected placement, foreign replacement, client-predicted
break, rejected break, server-confirmed removal, and missing confirmation. Gate
`20260905-160008-tests` freshly executed 658 tests: zero failures, 10 existing skips.

Protocol limitation: a concurrent replacement with the identical block state and
no observable intermediate update cannot be distinguished from the acknowledged
support by this client protocol. This does not justify deleting untracked blocks.
The patch has not been copied into OneBlock or released; the final limited
validation and independent review are recorded below.

The next run `4ecc1f2a` (`20260905-160112-suite`) still ended STALLED. Routing
reached the support, but a generic 100-tick idle nudge interrupted barehand
Survival cobblestone mining before its 200-tick break could finish. The generic
120-tick break-branch starvation guard had the same issue. Both now recognize
the helper's concrete current mining target; an input intention alone is not
enough. The getter requires an active controller break, matching live hit,
present player, no menu and a non-AIR target, and stop clears its state. The
existing material/tool-dependent deadline remains and temporary branch yields
no longer reset the same target's accumulated budget.

Run `f7815303` (`20260905-160727-suite`) ended FROZEN at 2,040 ticks, with all
120 target blocks present. Its independent full server-region comparison passed:
120 black stained glass and 20,415 AIR cells, including both former supports.
`f7815303-removed-scaffolds.log` additionally records server AIR at the two exact
coordinates. This exposed a bench detector error: its 200-tick no-motion/no-look
test assumed slow mining would turn the head. The body and aim correctly stay
steady for a 200-tick barehand break. The detector now treats the concrete live
mining state as work, preserving the 200-tick idle threshold and all overall
stall/time budgets. This run remains archived as FROZEN; it is not rewritten as
SUCCESS. The new fixture hash explicitly records this instrument correction.

Server-confirmed ownership release now logs its exact coordinate and resulting
state. The existing `broke=N` diagnostic counts break-intention ticks, not actual
removed blocks; it must not be presented as a removal count. Unit gate
`20260905-161419-tests` passed 658 tests, zero failures and 10 existing skips.
